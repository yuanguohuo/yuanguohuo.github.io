基本概念 (1)

仓库结构 (1.1)

本地仓库主要包含 2 部分：

  • git版本库（repository）：.git 目录
  • 工作区（working directory）：.git 目录之外的部分

涉及的“空间”有四个：

  • A. 工作区（在本地）
  • B. 本地分支（在本地）
  • C. 远程跟踪分支（在本地）
  • D. 远程分支（在远程，例如 github 上的分支）

注：这是简化模型，省略了暂存区（index）。下文 merge/rebase/reset 写回工作区时，通常也会同步更新 index。

远程跟踪分支 (1.3)

远程跟踪分支在本地，用于跟踪远程仓库（例如名为 “origin” 的远程仓库）的分支。远程跟踪分支（本地的跟踪者）与远程分支（远程的被跟踪者）的对应关系定义在 remote 的 refspec 中：

github上远程仓库的分支 本地的远程跟踪分支
master origin/master
dev origin/dev

… origin/…

注意 refspec 两边不在同一个库里。它的格式是 +<src>:<dst>：

  • <src>（这里是 refs/heads/*）在远程仓库的命名空间里解析；fetch 时 git 先问远程仓库“你有哪些 ref”（zhuhai：这是什么意思？），再用这个模式去匹配远程报来的列表；
  • <dst>（这里是 refs/remotes/origin/*）在本地库的命名空间里；
  • 开头的 + 表示强制更新，允许远程跟踪分支被 non-fast-forward 地覆盖，例如：上游——即 github 上的远程仓库——被 force push 过，fetch 还能成功，覆盖本地的远程跟踪分支（改写其历史）；

一个容易产生迷糊的地方在于：你可以在本地 repository（.git 目录）中看到左半边 refs/heads/（即本地分支部分），所以，可能觉得 refspec 是本地分支与远程跟踪分支的对应关系（见第1.4节）。实际上，这是错误的，因为 refs/heads/ 这个路径在两个库（本地仓库和 github 上的远程仓库）里都存在，长得一模一样，而 refspec 指的是远程仓库。也就是说，<src> 和 dst 是相对各自库的命名空间：

远程仓库里并没有 refs/remotes/（因为它不需要跟踪你）；只有你的仓库才有（因为你要跟踪远程仓库）。所以 refspec 两端不仅方向不同，命名空间也不重合。

  • merge: 远程仓库的分支（这里是 master），refs/heads/master 在远程仓库的命名空间里解析；

在 git clone 时，会自动为默认分支写上这段。

还有一些其它方式设置上游：

  • 创建分支时设置上游：

    • 命令：git switch -c bugfix origin/bugfix
    • 解释：origin/bugfix 是新分支的起点；起点是远程跟踪分支时会自动设置上游（branch.autoSetupMerge 默认开启；--no-track 选项可以禁止这一行为）；
    • 注意：新分支起点 {remote}/{branch} 是一个远程跟踪分支名（而不是远程分支名），git 设置的上游是远程分支，它会使用“远程跟踪分支与远程分支”的对应关系，做一次换算。

  • 为当前分支设置上游：

    • 命令：git branch -u origin/bugfix
    • 解释：origin/bugfix 是 -u 的参数，全称是 --set-upstream-to=origin/bugfix；
    • 注意：上游参数形式是 {remote}/{branch}，它是一个远程跟踪分支名（而不是远程分支名），git 会使用“远程跟踪分支与远程分支”的对应关系，做一次换算。

  • 推送时设置上游：

    • 命令：git push -u <remote> <src>[:<dst>]
    • 解释：这里 -u 是选项，没有参数，全称是 --set-upstream，表示把 <src> 的上游设置成远程仓库 <remote> 的 <dst> 分支；
    • 注意1：与上面两个命令不同，这里不需要换算——<remote> 和 <dst> 已经分别给出了远程仓库名和远程分支名；
    • 注意2：-u 只在 <src> 是本地分支或 attached HEAD 时起作用；若用 tag、commit id 或 detached HEAD 做 <src>，-u 被静默忽略（另外，commit id 和 detached HEAD 做 <src> 时不能省略 <dst>，必须写成 refs/heads/... 全名，否则 push 本身失败，加不加 -u 都一样）；
    • 注意3：若 <dst> 缺省，则为与 <src> 同名的远程分支（若 <src> 是本地分支或 attached HEAD）。

commit id (1.5)

每个 commit 都有一个唯一的 id，例如：

它本质上是一个 SHA-1 哈希值，由 git 根据 commit 的内容计算得出，所以也叫 commit hash.

是对哪些信息的哈希呢？

  • tree：本次提交对应的目录树快照；
  • parents：父 commit 的 id；
  • author：作者、时间；
  • committer：提交者、时间；
  • commit message：提交信息。

只要其中任何一项发生变化，生成的 commit id 就会不同。这也是为什么 rebase 会改变 commit id：rebase 会创建新的 commit 对象，parent 关系变了，hash 自然不同。

完整 id 有 40 个十六进制字符，日常使用时 git 允许使用前缀缩写，只要不产生歧义即可。例如：

git log --oneline 通常显示 7 位，大型仓库可能需要更多位才能唯一标识。可以用 git rev-parse --short HEAD 查看当前仓库的默认缩写长度。

为什么 commit id 很重要？

  • 唯一标识：每个 commit id 全局唯一，可以精确指向某个提交。
  • 不可篡改：commit id 由内容哈希决定，修改任意内容都会产生新的 id，旧 id 对应的对象仍然保持不变。
  • 引用基础：分支、tag、HEAD 本质上都是指向某个 commit id 的指针。
  • DAG 的边：commit 通过 parent 字段存储父 commit 的 id，从而构成有向无环图。

查看 commit id：

与”不可变”的关系：因为 commit id 由内容决定，所以commit 对象一旦创建就无法被修改。如果修改了提交信息、作者或文件内容，git 会创建一个全新的 commit 对象，拥有新的 id。这就是 git 说”commit 不可变”的底层原因——不是不能改变历史，而是改变历史的方式是创建新对象，而不是修改旧对象（见第1.6节）。

parent 关系 (1.6)

除了 root commit 之外，每个 commit 都有 parent；

  • 普通的 commit 有一个 parent；
  • merge commit 有多个 parent：在当前分支上执行 merge $\text{branch}_1 \quad \text{branch}_2 \quad \cdots \quad \text{branch}_n$ 时，产生的 merge commit 通常有 $n+1$ 个 parent——包括当前分支自己的 merge 前的最新 commit。

通过 parent 关系，所有的 commit 构成一张有向无环图（DAG）。一经提交，一个 commit 就作为一个顶点，连到图中了。已经存在的 commit 对象无法改变，但图的结构可以通过改变，例如 rebase：

  • 把需要移动的 commit 拷贝到新位置；
  • 移动分支指针，旧 commit 不再被任何分支引用；
  • 若旧 commit 不再被任何分支、tag、reflog 或 HEAD 引用，它可能被 git gc 物理地删除；

虽然 git 强调 commit 不可变，但对最终用户而言，创建新 commit 并 gc 旧 commit 等价于更改图的结构——把一个顶点移动到别的位置，而且它的 hash（即commit id）也变了。

除了 rebase 之外，还有 amend、filter-branch 等少量改写历史的操作。不考虑它们的话，commits 通过 parent 关系构成的 DAG 是固定的；新的提交只会在原有图上添加节点和边，不会修改已有的 commit 对象（不修改已有部分）。

这张图才是 Git 的根基。学习分支、HEAD 等概念时，要始终记得：分支可以指向图中的任意 commit；HEAD 可以是 attached，即引用某个分支，也可以是 detached，即直接存储一个 commit id。但无论指针如何移动，已有的 commit 对象本身不会改变；从某个 commit 沿 parent 回溯得到的历史（git log）也不会改变——除非执行 rebase、amend、filter-branch 等改写历史的命令。

分支 (1.7)

分支到底是什么？

本质上，分支就是 refs/heads/ 下的一个引用（ref）：通常存放为 .git/refs/heads/ 里的一个文件，但也可能被打包进 .git/packed-refs，此时上述文件不存在（用 git rev-parse dev 查看最可靠）。它不会自动记录“整个分支链”，也不会记住 [a] -> [f] 这条线；它只记住：当前分支顶端是哪一个 commit（commit id）。所以，分支就是一个标签（分支名）加一个指向某个 commit 的指针。

Git 里分支的底层实现就是一个指向 commit 的指针，而不是一个文件夹、一条链表或一棵树。既然分支只是一个commit id，根本不是“树枝”一样的东西，它为什么叫 branch（分支）？

因为，从使用者的视角，分支是一条独立的开发线，可以并行改代码、再合并。可以这样比喻：

  • 把 commits 想成时间线上的存档点：a, b, c, d, e, f, …
  • 分支就是贴在这个时间线上的“标签”，如上图：
    • 刚创建 dev 时，[c] 上同时贴着 “master” 和 “dev”；
    • 之后 dev 提交到 [d]，”dev” 标签移到 [d]；
    • master 提交到 [e]，”master” 标签移到 [e]；
    • dev 继续提交到 [f]、[h]，”dev” 标签先移到 [f] 最终移到 [h]；
    • master 提交到 [g]，”master” 标签移到 [g]；
    • master 合并后经过 [M]，最终指向 [i]，”master” 标签经 [M]，最终移到 [i]；
  • 这样，就形成了 dev 分支和 master 分支；
  • 注意1：
    • master 不是 [a], [b], [c], [e], [g], [M], [i] 这一整串；dev 也不是 [c], [d], [f], [h] 这一整串；它们各自只是一个 commit id；
    • 分支标签同一时刻只贴在一个 commit 上；提交后标签会移动，所以之前贴过的 commit 不再被该分支“指向”，但仍属于它的历史；
    • 没贴过某个标签的 commit 也能成为对应分支的历史：[d], [f] 从未贴过 “master” 标签，但属于 master 的历史（因为 [M] 有两个父 commit，一个来自 master 方向，另一个来自 dev 方向）；
    • 分支也不对应第1.6节中说的 DAG 中的某条路径；

实际上，分支就是 DAG 上的一个指针：完全可以通过 reset 让分支指向任何 commit 上，并从那里开始演进。并且，reset 到某个地方之后，看到的历史就是从那个地方按 parent 关系往前回溯。

常见基本操作 (2)

fetch (2.1)

git fetch {remote-name} {remote-branch}，例如 git fetch origin master

  • 从名为 “origin” 的那个 remote 库（github 上的 “project” 库）的 master 分支下载最新提交；
  • 更新本地对应的远程跟踪分支（对应关系见前文，本例中就是 origin/master）；
  • 不会合并到当前本地分支；
  • 也不会修改工作区；
  • 即：D -> C;（见第1.1节的四个空间）

merge (2.2)

git merge 远程跟踪分支，例如 git merge origin/master

  • 来源（远程跟踪分支 origin/master）+ 当前分支（HEAD 指向的本地分支，如 feature）= NewMergeCommit；
  • 更新当前分支（feature）到 NewMergeCommit；
  • 并且 把 NewMergeCommit 的内容写回工作区；
  • 即 C + B -> B; B -> A;（见第1.1节的四个空间）

注：若满足 fast-forward 条件（当前分支是来源的祖先），默认不产生 NewMergeCommit，只把当前分支指针移到来源的 commit（见后文 fast-forward），并且内容写回工作区；

git merge 本地分支，例如 git merge master

  • 同上，只是“来源”不是远程跟踪分支，而是本地分支（master）；
  • 若当前分支（HEAD 指向的本地分支）是 feature，则：本地分支（master）+ 本地分支（feature）= NewMergeCommit；
  • 更新当前分支（feature）到 NewMergeCommit；
  • 并且 把 NewMergeCommit 的内容写回工作区；
  • 即 B1（来源） + B2（当前分支）-> B2; B2 -> A;（见第1.1节的四个空间）

rebase (2.3)

git rebase 远程跟踪分支，例如 git rebase origin/master

  • 把当前分支（HEAD 指向的本地分支，如 feature）上的新commits 放到来源（远程跟踪分支 origin/master）的新 commits 的后面；
  • 不产生 NewMergeCommit；
  • 并且 把内容写回工作区；
  • 也是 C + B -> B; B -> A; 只是没有 NewMergeCommit;

git rebase 本地分支，例如 git rebase master

  • 同上，只是把来源换成本地分支；
  • 也是 B1（来源） + B2（当前分支）-> B2; B2 -> A; 只是没有 NewMergeCommit；

pull (2.4)

git pull 远程名 远程分支，例如 git pull origin master

  • 默认（未配置 pull.rebase、pull.ff 等）等价于 git fetch origin master + git merge origin/master；
  • 实际行为受配置影响：
    • pull.rebase=true 时相当于 git pull --rebase；
    • pull.ff=only 时只允许 fast-forward，分叉则失败；
  • 新版本 git 在两边分叉且未配置上述选项时，会报错：要求明确指定 merge 还是 rebase；

git pull –rebase 远程名 远程分支，例如 git pull –rebase origin master

  • 等价于 git fetch origin master + git rebase origin/master

对比 merge 与 rebase (2.5)

  • merge “来源”到“当前分支”

    • 保留两方的提交顺序，合并产生 NewMergeCommit；
    • 双方的 commit hash (commit id) 都不变；
    • 当前分支指向 NewMergeCommit；
    • 分叉后合并，历史有分支形状；
    • 适用：合并功能分支到主分支（保留完整的分支历史，方便追溯）、多人协作的共享分支（不改写历史，避免冲突）
    • 可以对已经推送到远程的分支做；

  • 把“当前分支” rebase 到“来源”之上

    • “来源”的 commits 在前，当前分支的 commits 在后；保留各自的相对提交顺序（把当前分支上的 commits 整体“搬到”来源分支的顶端）；不产生 NewMergeCommit；
    • “来源”的 commit hash (commit id) 不变；当前分支独有、被搬动（重放）的那些 commits 会得到新的 hash；
    • 分叉点之前的共同 commits 不变；若当前分支本来就基于来源的顶端，则什么都不变；
    • 当前分支指向最后的commit（当前分支的最新commit、被排在最后）；
    • 历史被重写，变成一条直线；
    • 适用：本地开发时同步远程最新代码（保持线性历史，干净清爽）、个人分支还没 push（整理提交记录，让历史更清晰）
    • 不要对已经推送到远程的分支做！因为会改写历史，别人拉的时候会冲突！

  • 总之：rebase 是“整理自己的历史”，merge 是“整合别人的历史”；自己的、还没 push 的 commits，随便 rebase；别人的、已经 push 的 commits，用 merge。

对比 fast-forward 与 non-fast-forward (2.6)

  • fast-forward:
  • non-fast-forward (–no-ff 选项)：
    • 不满足 fast-forward 条件（当前分支有来源没有的新提交，即两边分叉）或者满足但 merge 时添加 --no-ff 选项；
    • 注意：能否 fast-forward 只看提交历史的祖先关系，与是否冲突无关；分叉后合并才可能出现冲突；
    • 会产生一个 MergeCommit；
    • 好处是，保留分支信息；

HEAD 是什么？

HEAD 就是 .git/HEAD 这个文件，它记录“我当前在哪里”。它有两种形态：

  • 正常状态（attached）：里面存的是一个分支名，即所谓的符号引用（symbolic ref）：

这是一次间接：HEAD -> 分支名 -> commit id。

  • detached HEAD（游离状态）：里面直接存一个 commit id，不经过任何分支：

HEAD 的两个作用

  1. 提交时的父 commit：新 commit 的 parent 就是 HEAD 当前所指的 commit；
  2. 决定提交后移动谁：正常状态下，提交会让 HEAD 所指的那个分支指向新 commit（HEAD 本身的内容不变，仍是 ref: refs/heads/xxx）；detached 状态下，移动的是 HEAD 自己。

同理，git reset 正常状态下移动的是当前分支，detached 状态下移动的是 HEAD（见前文 reset 小节）。

基于 HEAD 的 commit 坐标写法

写法 含义
HEAD 当前 commit
HEAD^、HEAD^1 第一个父 commit
HEAD^2 第二个父 commit（只有 MergeCommit 才有，指向被合并进来的那一方）
HEAD~1 等同 HEAD^，往上一代
HEAD~2 往上两代，即 HEAD^^（始终沿第一父走，不会拐到被合并的分支上）
HEAD@{2} reflog 里 HEAD 两次变动之前的位置（git reflog 可查看）
ORIG_HEAD 上一次 reset/merge 等危险操作之前 HEAD 的位置，用于反悔

以第2.6节 non-fast-forward 那张图为例，master 指向 MergeCommit [M] 时：HEAD^1 是 [g]（master 方向），HEAD^2 是 [f]（dev 方向），HEAD~2 是 [e]（继续沿第一父）。

detached HEAD：怎么进入、有什么风险

查看历史提交的内容、二分查找（git bisect）时会处于这个状态，本身没有问题。风险在于此时的提交没有任何分支指向它：

一旦切走，HEAD 改指别处，这个 commit 就不再被任何引用指向，git log 看不到，久置会被 gc 清理（短期内还能用 git reflog 找回）。所以在 detached 状态下做了提交又想保留，切走之前先给它一个分支：

git reset –hard/–soft/–mixed CommitID

三种模式都会把当前分支（reset 前 HEAD 所指的那个分支）移到 CommitID；HEAD 本身不变，仍是 ref: refs/heads/<当前分支>。区别在于是否重置 index 和工作区。被移走的 commits 还可以通过 ORIG_HEAD 或 git reflog 找回。

注意：CommitID 只是“移到哪里”的目标，与它属于哪个分支的历史无关；reset 不会切换分支。例如当前在 dev 分支，对 master 历史上的某个 commit 执行 reset：

此时 git log --decorate 会显示 [m2] (HEAD -> dev, master)：dev 和 master 同时指向 [m2]，但当前分支仍是 dev，之后的提交只会移动 dev。

若处于 detached HEAD（HEAD 直接存着一个 commit id，而不是 ref: refs/heads/...），则 reset 移动的是 HEAD 自己，不涉及任何分支。

  • hard: 回到 CommitID，工作区也会被重置，已跟踪文件中未提交的修改（包括已 add 的）都会丢失！
    • 当前分支移到目标 commit
    • index（暂存区）重置为目标的快照，已 add 的内容被清除
    • 工作区重置为目标的快照，工作区修改被覆盖
    • 未跟踪（untracked）文件不受影响
  • soft: 回到 CommitID + 从 CommitID 到当前 index 的 diff（staged）
    • 不改 index，也不改工作区，所以不丢失任何修改
    • 从 CommitID 到当前状态的 committed 修改：变成 staged 状态
    • 从 CommitID 到当前状态的 staged 修改：仍为 staged 状态
    • 从 CommitID 到当前状态的 unstaged 修改：仍为 unstaged 状态
    • 注意：若同一文件既有被撤销的提交修改，又有之后的 staged 修改，二者合并为一份 staged 修改（中间版本只保留在原 commit 里）
  • mixed（默认模式）: 回到 CommitID + 从 CommitID 到工作区的 diff（unstaged）
    • 工作区不变；index 重置为目标的快照
    • 从 CommitID 到当前状态的 committed 修改：变成 unstaged 状态（工作区中有这些内容）
    • 从 CommitID 到当前状态的 staged 修改：变成 unstaged 状态（前提是工作区中也有这些内容，否则会丢失见下面注意点）
    • 从 CommitID 到当前状态的 unstaged 修改：仍为 unstaged 状态
    • 注意：不保证不丢失：只存在于暂存区、与工作区不同的内容会丢失（例如 add 之后又在工作区把它改掉或删掉）

reset 的本质：给引用赋值

reset 做的事只有两步：

  1. 把当前分支这个引用的值改成 CommitID（detached HEAD 时改的是 HEAD 自己）；
  2. 按模式决定是否把 index、工作区刷成该 commit 的快照（见上面三种模式）。

“赋值”意味着它对 CommitID 没有任何历史要求：

  • CommitID 可以是任意形式的 commit 坐标：HEAD~2、cc591ad、master、origin/master、other 都一样，git 只解析出一个 commit id；
  • 不要求与当前分支有共同祖先。即使两条历史毫无交集（如 git switch --orphan 造出来的分支），reset 也会成功；
  • 对比：merge 需要找 merge-base 做三方合并（无关历史还要 --allow-unrelated-histories），rebase 需要找分叉点来决定重放哪些 commits —— 它们都依赖历史关系，reset 不依赖。

reset 不是切换分支

git reset --hard other 执行后，当前分支仍然是 dev，只是 dev 指向了 other 所指的那个 commit：

命令 改的是什么 之后当前分支
git switch other HEAD（ref: refs/heads/dev -> ref: refs/heads/other） other
git reset --hard other dev 这个引用的值（指向 other 的 commit） 仍是 dev

即 switch 动 HEAD、不动分支指针；reset 动分支指针、不动 HEAD。

reset 之后，git log dev 看到的是 other 那条历史（因为历史是从分支指针往父提交回溯出来的），dev 原来的 commits 从 dev 不再可达。两个分支此刻指向同一 commit，但之后提交只会移动 dev。

所以“把当前分支 reset 到另一个分支上”是可行的，但它的含义是“让当前分支改指过去、丢弃自己原来的线”，不是“切过去”。这类操作要当心：

  • 原有 commits 只能靠 ORIG_HEAD / git reflog 找回，git log 已经看不到，久置会被 gc 清理；
  • 这是改写历史，分支若已 push，再推需要 --force，会影响已拉取该分支的人；
  • 用 --soft/--mixed 时工作区不变，会产生一个“删掉对方文件、新增自己文件”的巨大 diff；
  • 日常想换开发基线，用 git switch 或 git rebase --onto；reset 的常规用途是在同一条线上前后挪动。

git switch [-c] BranchName

  • 切换到分支 BranchName；
  • 选项 -c 表示 create（新建新分支并切换到它）；所以，切换到已存在分支不加-c；
  • 取代 git checkout（不要再用 git checkout BranchName）！

以一次真实投稿为例：Jira 编号 DAOS-19869，功能分支 DAOS-19869-manual-discard，官方仓库 daos-stack/daos，个人 Fork yuanguohuo/daos。
命令本身是通用的，换项目只需替换编号、分支名和仓库地址。

两个远端的分工

开源项目基本都是「Fork + PR」模型，本地仓库要登记两个远端：

远端 地址 权限 用途
origin github.com/yuanguohuo/daos（个人 Fork） 可读可写 push 功能分支
upstream github.com/daos-stack/daos（官方） 只读 fetch 官方最新代码

数据流向是一个环：

本地不直接往官方 push（也没有权限），代码进官方的唯一途径是 PR。
origin 和 upstream 只是约定俗成的名字，没有任何特殊语义，就是 .git/config 里的两段配置（见第 1 节）。

一、建仓与确定起点

逐条解读：

  • clone --branch master <Fork 地址>：Fork → 新建的本地仓库。clone 会自动把来源远端命名为 origin，并写入第 1 节那条 fetch refspec，于是 refs/remotes/origin/* 一并建好。--branch master 只决定 clone 完 checkout 哪个分支。投稿需要完整历史，不要用 --depth。
  • remote add upstream <官方地址>：仅在 .git/config 里加一段地址配置，不下载任何代码。
  • fetch upstream master：官方库的 master → 本地对象库，并更新远程跟踪分支 upstream/master。它不动任何本地分支，也不会更新你 Fork 上的 master。所谓“Fork 落后于官方”对投稿没有影响，因为基线取自 upstream/master 而不是 Fork。
  • switch --no-track -c <分支名> upstream/master：以刚取到的官方基线新建功能分支并切换工作区。--no-track 是关键：不加它，git 会顺手把这个分支的上游配成 upstream/master（即第 1 节的 branch.*.remote / branch.*.merge），之后无参数的 git push / git pull 目标就错了——应该对自己的 Fork，而不是官方。

分支名用 DAOS-<Jira 编号>-<主题>，这是 DAOS 的约定；别的项目看它自己的贡献指南。

git status --short 每行开头是两列 XY：X 是 index 相对 HEAD，Y 是工作区相对 index。

输出 含义
M f 改了但没暂存

暂存：

不要用 git add .：会把测试日志、覆盖率报告、补丁文件、个人配置一起塞进提交。

一个常见误解：git add 之后 git diff 变空，不代表改动丢了——它只是跑到 index 里去了，用 git diff --cached 看。

确定 PR 改动范围要用分叉点，而不是 HEAD^：

git merge-base A B 给出两条线的最近共同祖先。HEAD^..HEAD 只在「PR 恰好一个提交」时才等价，多提交的 PR 用它会漏掉前面的提交。

三、创建提交

解读：

  • 四个环境变量写在命令前面，只对这一条命令生效，不改全局也不改仓库配置。适用场景：本机默认身份是公司邮箱，而社区投稿要用个人公开身份。
  • GIT_AUTHOR_* 是原作者（代码是谁写的），GIT_COMMITTER_* 是本次创建提交的人。平时两者相同；rebase、amend、别人代为提交时会不同。两个都要核对。
  • 多个 -m 按顺序拼成提交信息：第一个是标题，其余是正文段落，中间自动空一行。DAOS 要求标题含 Jira 编号和 component、不超过 62 字符，正文按约 70 列换行。
  • -s 自动添加 Signed-off-by: 一行，表示 DCO 声明（我有权提交这段代码）。它不是 GPG 签名（那是 -S），也不会让 github 显示 Verified。DAOS 的 DCO 检查就看这一行。
  • 邮箱会随提交永久公开。可以用 github 提供的 noreply 地址，但不能自己编一个。
  • 本机如果装了 hook（拼写检查、版权行、凭据泄露扫描），让它正常跑。不要用 --no-verify 绕过，拦住了就去处理原因。

提交后确认：

git log -1 默认只显示 Author，看不到 committer；--format=fuller 才会把两者都列出来。用环境变量改身份时，必须用它核对，否则很容易出现 Author 改了、Committer 还是公司邮箱的情况。

四、推送到 Fork

解读：

  • 这条等价于 git push origin refs/heads/DAOS-19869-manual-discard:refs/heads/DAOS-19869-manual-discard。按第 1 节的镜像规则，push 时 <src> 在本地、<dst> 在远程——所以左边才是你的本地分支。远端没有这个分支时会新建，回显 [new branch]。
  • -u（--set-upstream）在 .git/config 写入这个分支的上游配置，指向 origin/DAOS-19869-manual-discard。之后 git push / git pull 可以不带参数，git status -sb 也能报 ahead/behind。第一次推送加 -u，之后不用再加。
  • push 只上传已提交的历史：没提交的测试日志、覆盖率报告不会上去；但已经提交进历史的敏感信息会上去，而且删不干净。
  • HTTPS push 提示 Password 时，要的是令牌（token）而不是 github 登录密码。令牌不要写进仓库 URL、代码或文档。
  • push 不会自动创建 PR。

git status -sb 的 ahead/behind 是把本地分支和本地的 origin/<分支> 比，而那只是上次 fetch/push 时的快照——远端被别人改了，它也不知道。要确认远端真实指向，只能用 git ls-remote：它直接问远端，并且不写本地任何引用。本次核对到 Fork 上的 SHA 与本地 HEAD 同为 e313e8a10…，才确认不用再推一次。

五、PR 之后

跟进官方更新：

第二条实测过：功能分支从 master 分出来时退出码是 0，master 又有新提交后变成 1。注意它只回答「是否包含」，不改任何东西。

真要吸收上游更新，再做 merge 或 rebase（项目有偏好就按项目的来），然后重新验证——不要为每次上游变动自动 rebase；PR 没冲突、维护者没要求时，先推进 CI 和 review 更重要。

按 review 意见改代码时：

  • --amend 不是「修改」原提交，而是用新内容造一个新提交替换它，所以 SHA 必然变（旧的还能在 reflog 里找到）。
  • 远端已有旧提交，新历史不是它的后代，普通 push 会被拒（non-fast-forward，见第2.6节的 fast-forward 条件）。
  • 用 --force-with-lease 而不是 --force：前者会先检查「远端现在的值是否还是我上次见到的值」，若别人动过就拒绝推送，避免覆盖别人的提交。
  • 收到 non-fast-forward 报错时先搞清原因，不要条件反射地 force。

命令速查

命令 一句话解读
git remote add upstream <url> 只登记地址，不下载代码
git fetch upstream master 官方 → 本地对象库 + upstream/master，不动本地分支
git switch --no-track -c <分支> upstream/master 以官方基线建分支，且不把上游设成官方
git status --short 两列 XY：index 相对 HEAD、工作区相对 index
git diff / git diff --cached 工作区 vs index / index vs HEAD
git add -u 只收已跟踪文件的改动，新文件要显式 add
git merge-base HEAD upstream/master 求分叉点，确定 PR 的真实改动范围
